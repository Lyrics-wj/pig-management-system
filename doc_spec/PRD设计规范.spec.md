# 产品设计约束

本文档约定 **2024年蓬溪县生猪数字化管理平台** 项目在设计与评审新功能时的流程与产出物，确保在进入技术设计与开发前，先基于现有功能做调研、产出产品需求文档（PRD），并通过可交互 HTML 原型确认功能与体验。

---

## 一、适用范围

- 所有**新增业务功能**或**对现有功能做较大行为/交互变更**时，必须遵循本约束。
- 小范围 Bug 修复、文案调整、配置变更可不走完整流程，但涉及接口或页面结构变更时仍建议有简要需求说明。

---

## 二、设计流程（强制顺序）

新功能设计必须按以下顺序执行，不得跳过或颠倒：

```
1. 调研现有功能  →  2. 撰写 PRD  →  3. 产出可交互 HTML 原型  →  4. 评审确认  →  5. 进入技术设计/实现
```

| 阶段 | 产出物 | 说明 |
|------|--------|------|
| **1. 调研现有功能** | 调研结论或附录 | 基于 `doc_spec/现有业务说明.spec.md` 及实际代码/页面，明确与哪些现有模块、接口、页面相关；复用点与差异点。 |
| **2. 撰写 PRD** | 产品需求文档（.md） | 按本文 **三、PRD 必备结构** 撰写；存放于功能对应目录（如 `openspec/changes/<变更名>/` 或统一 `doc_product/`）。 |
| **3. 可交互 HTML 原型** | 单页或多页 .html | 能演示关键流程、可点击、可填写表单；用于与产品/业务方确认「做什么、怎么用」，再进入技术设计。 |
| **4. 评审确认** | 评审结论 | PRD + 原型经确认后，方可进入技术设计（如 `design.md`、`proposal.md`）与开发。 |
| **5. 技术设计/实现** | design.md、代码等 | 遵循 `doc_spec/项目整体代码约束.spec.md`、`doc_spec/现有数据库说明.spec.md`、`doc_spec/现有业务说明.spec.md` 等；若使用 OpenSpec 流程则按 `openspec/changes/` 约定。 |

---

## 三、PRD 必备结构

产品需求文档至少包含以下章节，缺一不可：

> **⚠️ 多功能 PRD 编写规范（强制）**
>
> 若一份 PRD 中涉及**多个独立功能**（如「养殖档案管理」「出栏申报」「防疫记录」等），**每一个功能必须独立、完整地按照以下全部章节（3.1 ～ 3.6）进行编写**，不得多个功能共用同一章节、合并描述或相互引用代替。
>
> - 每个功能作为一个独立的顶级章节（如「功能一：XXX」「功能二：XXX」），其下完整包含 3.1 ～ 3.6 全部子章节。
> - 禁止以「同上」「参见功能一」「与 XX 功能一致」等方式省略任何章节内容。
> - 各功能的数据模型、字段定义、校验规则、交互逻辑须各自独立描述，即使存在相似之处也须完整写出。
> - 功能间若存在依赖或关联，在各自的 3.1「关联现有模块/功能」中注明，不以此替代本功能的完整描述。

### 3.1 基本信息

- **功能名称**：简短中文名称。
- **关联现有模块/功能**：列出与本需求相关的现有功能（参考 `现有业务说明.spec.md` 中的模块与接口）。
- **目标用户/场景**：谁在什么场景下使用。**角色名称与角色编码必须引用 `需求梳理/第0阶段-多端权限架构/全局-角色与权限体系.md` §1.1 角色总览中的定义**，不得自行新造角色名或编码。

### 3.2 目标与范围

- **目标**：本功能要达成的业务目标（可多条）。
- **非目标（Non-Goals）**：明确不做的内容，避免范围蔓延。

### 3.3 现状与复用

- **现状简述**：相关现有功能的当前行为（接口、页面、权限等）。
- **复用与差异**：哪些直接复用（接口、组件、权限）、哪些需要新增或修改。

> **⚠️ 复用检查规范（强制）**
>
> 在撰写 PRD 之前，**必须**对照以下两份规范文档逐项排查可复用资源，并在本章节（3.3）中明确列出排查结论，不得跳过或以「暂无复用」笼统带过：
>
> **1. 接口复用检查（对照 `doc_spec/现有业务说明.spec.md`）**
>
> - 逐一排查现有系统中是否已有功能相近的接口（含认证、系统管理、业务模块等所有章节）。
> - 对每个本次需求所需的接口操作（列表、详情、新增、修改、删除、导出等），明确说明：
>   - ✅ **直接复用**：接口已存在且满足需求，在 3.4.4 接口列表备注列标注来源（`见现有业务说明.spec.md §X.X`），不重复定义。
>   - 🔧 **改造复用**：接口已存在但需扩展字段或行为，在 3.3 中说明改造点，在 3.4.4 中标注「基于现有接口改造」。
>   - 🆕 **新增**：确无可复用接口，说明原因，在 3.4.4 中正常定义新路径。
>
> **2. 数据库表复用检查（对照 `doc_spec/现有数据库说明.spec.md`）**
>
> - 逐一排查现有表结构中是否有可直接使用或扩展的表（含系统表、业务表、字典表等）。
> - 对每个本次需求涉及的数据实体，明确说明：
>   - ✅ **直接复用**：使用现有表，在 3.4.2 数据模型中标注「复用现有表 `表名`，见现有数据库说明.spec.md §X.X」。
>   - 🔧 **扩展复用**：在现有表上新增字段，在 3.4.2 中列出新增字段，并在数据库规范文档中同步更新。
>   - 🆕 **新建表**：确无可复用表，说明原因，按 3.4.2 完整定义新表结构。
>
> **复用检查结论格式（在 3.3 中按如下格式列出）：**
>
> | 检查项 | 现有资源 | 复用结论 | 说明 |
> |--------|---------|---------|------|
> | 用户列表接口 | `/system/user/list` | ✅ 直接复用 | 见现有业务说明.spec.md §3.1 |
> | 养殖记录表 | 无 | 🆕 新建表 `pig_breed_record` | 无现有表满足需求 |
> | 字典数据接口 | `/system/dict/data/type/{dictType}` | ✅ 直接复用 | 猪品种、状态等下拉均复用字典接口 |

### 3.4 功能需求

- **功能列表**：按用户故事或功能点列出，每条可标优先级（P0/P1/P2）。
- **关键流程**：主流程说明（含异常分支，如校验失败、无权限）。
- **交互与界面要点**：主要页面/弹窗、关键操作、必填项与校验规则。

#### 3.4.1 功能流程逻辑

- **业务流程图**：描述业务流转的泳道图或状态机。
- **逻辑规则**：关键算法、自动计算逻辑、状态流转触发条件、按钮展示/点击逻辑。

#### 3.4.2 数据模型与字段定义

- **核心实体**：主要业务对象及其关系。
- **字段明细**：字段名（中文）、字段名（英文）、类型、长度、必填项、默认值、取值范围/枚举值、说明。

> **⚠️ 字段定义写作规范（强制）**
>
> 在定义字段的取值范围、枚举值、校验规则、说明等内容时，**严禁使用任何模糊描述词**，包括但不限于：
>
> - 禁止使用「等」（如 ❌「教学楼、实验楼等」→ ✅ 逐一列出全部枚举值）
> - 禁止使用「大概」「约」「左右」「差不多」（如 ❌「大概 20 个字符」→ ✅「最大长度 20 个字符」）
> - 禁止使用「若干」「部分」「某些」「一些」（如 ❌「若干字段不可为空」→ ✅ 明确列出每个必填字段）
> - 禁止使用「可能」「也许」「一般来说」等不确定表述（如 ❌「一般来说不超过 100」→ ✅「最大值 100」）
>
> **正确示例：**
>
> | ❌ 模糊写法 | ✅ 规范写法 |
> |------------|------------|
> | 楼宇类型：建筑物、构筑物等 | 楼宇类型枚举值：`BLDG_TYPE_01` 建筑物、`BLDG_TYPE_02` 构筑物、`BLDG_TYPE_03` 土地、`BLDG_TYPE_04` 附属设施（共4种，无其他） |
> | 面积大概不超过几万 | 占地面积：decimal(10,2)，单位㎡，最小值 0，最大值 99999999.99 |
> | 部分字段必填 | 必填字段：楼宇编号、楼宇名称、所属校区、楼宇类型、楼宇用途；其余字段选填 |
> | 状态等信息 | 状态：char(1)，`0` 启用，`1` 停用，仅此两种取值 |

#### 3.4.3 界面交互逻辑

- **交互细节**：悬停提示、点击反馈、加载状态、错误提示方式。
- **动效要求**：若有特殊转场或动画需明确说明。

> **⚠️ 界面交互强制规范**
>
> **1. 标签分类筛选（Tab/标签切换）**
>
> 凡页面存在标签（Tab）分类展示内容的场景，点击标签时必须**立即筛选并刷新下方展示内容**，不得需要额外点击「查询」「确认」等按钮触发。具体要求：
> - 标签切换为即时响应，切换后列表/内容区域自动重新加载，展示对应分类数据。
> - 切换过程中应有加载状态反馈（如 loading 遮罩或骨架屏），防止内容空白闪烁。
> - 当前激活标签需有明显选中态样式区分。
>
> **2. 新增/编辑表单字段完整性（强制）**
>
> 凡涉及新增或编辑功能的表单，**必须严格按照 3.4.2「数据模型与字段定义」中定义的字段全量体现**，不得遗漏任何字段，不得擅自增加未在数据模型中定义的字段。具体要求：
> - 表单字段与数据模型字段一一对应，字段名称、类型、必填性、枚举值均须与数据模型保持一致。
> - 若某字段在新增与编辑场景下行为不同（如编辑时不可修改），须在 PRD 中逐一说明，不得默认省略。
> - 字段顺序建议与数据模型定义顺序保持一致，如有调整须注明原因。
>
> **3. 自动回显字段的不可编辑规范（强制）**
>
> 凡字段值应由系统自动生成或关联数据自动回显（如编号、创建时间、创建人、关联名称等），**该字段在表单中默认呈现为只读/不可编辑状态**，不得渲染为可输入控件。具体要求：
> - 只读字段使用纯文本展示或禁用态输入框，视觉上与可编辑字段有明显区分。
> - 若特殊业务场景下该字段需允许手动修改，须在 PRD 中明确标注「允许手动编辑，原因：……」，否则一律按只读处理。
> - 自动回显字段包括但不限于：系统生成编号、创建时间、最后更新时间、创建人、所属组织（由登录上下文带入）等。
>
> **4. 表单提交前端校验（强制）**
>
> 凡涉及用户输入内容的功能（新增、编辑、搜索条件填写、多步骤向导等），在执行下一步操作（提交、保存、进入下一步、发起请求）之前，**必须先完成前端页面级校验**，校验通过后方可继续。具体要求：
> - **必填校验**：所有标记为必填的字段，提交前须检查是否已填写，未填写时阻断操作并在对应字段下方或旁边给出明确提示（如「XXX 不能为空」）。
> - **格式/范围校验**：有格式要求的字段（如手机号、身份证号、数字范围、日期合法性等）须在提交前完成格式验证，不合规时给出具体提示（如「手机号格式不正确」「数值不能超过 99999」）。
> - **业务逻辑校验**：存在字段间依赖关系的（如结束时间不得早于开始时间、数量不得超过库存上限），须在提交前完成联动校验，给出明确提示。
> - **校验时机**：建议在字段失焦（blur）时即时校验单个字段，提交时对全部字段做整体校验；不得仅依赖后端返回错误来提示用户。
> - **校验提示位置**：错误提示紧邻对应字段展示，不得仅用全局弹窗笼统提示「请检查表单」而不指明具体字段。
> - **多步骤场景**：分步骤表单中，每一步的字段须在点击「下一步」时完成当步校验，校验不通过不得跳转至下一步。

#### 3.4.4 接口路径定义（强制）

每个功能模块在 PRD 阶段须按以下规范统一定义所需接口路径，作为技术设计与前后端对接的基准。

**路径命名规则：**

```
/{业务域}/{子模块}[/{资源}/{操作}]
```

- **业务域**：对应功能所属的顶级业务域，使用小写英文，例如 `farm`（养殖）、`epidemic`（防疫）、`slaughter`（屠宰）、`statistics`（统计）、`system`（系统管理）。
- **子模块**：当前功能实体的英文复数或业务名词，使用小写驼峰或短横线，例如 `breed-records`、`vaccines`、`farms`。
- **资源/操作后缀**：仅在无法用标准 HTTP 方法语义表达时才追加，例如 `/changeStatus`、`/export`、`/importData`；标准 CRUD 不加后缀。

**标准 HTTP 方法对照：**

| 操作 | HTTP 方法 | 路径示例 | 说明 |
|------|-----------|----------|------|
| 分页列表 | GET | `/farm/breed-records/list` | 支持分页、筛选参数 |
| 详情 | GET | `/farm/breed-records/{id}` | 按主键查单条 |
| 新增 | POST | `/farm/breed-records` | 请求体为 JSON |
| 修改 | PUT | `/farm/breed-records` | 请求体含主键 |
| 删除 | DELETE | `/farm/breed-records/{ids}` | 支持批量，多个 id 逗号分隔 |
| 状态切换 | PUT | `/farm/breed-records/changeStatus` | 请求体含 id 与 status |
| 导出 | POST | `/farm/breed-records/export` | 返回 Excel 文件流 |
| 导入 | POST | `/farm/breed-records/importData` | 上传 Excel 文件 |
| 导入模板 | POST | `/farm/breed-records/importTemplate` | 下载模板文件 |
| 下拉选项 | GET | `/farm/breed-records/options` | 返回 id+name 列表，不分页 |

**PRD 中接口列表格式（每个功能须包含）：**

> 在功能的 3.4.4 章节中，以表格形式列出本功能涉及的全部接口，格式如下：

| 接口名称 | HTTP 方法 | 路径 | 请求参数摘要 | 响应数据摘要 | 备注 |
|----------|-----------|------|-------------|-------------|------|
| 分页查询养殖记录 | GET | `/farm/breed-records/list` | pageNum、pageSize、farmId、status | 分页列表+总数 | 数据权限按养殖场 |
| 新增养殖记录 | POST | `/farm/breed-records` | 见 3.4.2 字段定义 | 操作结果 | — |

> **⚠️ 接口路径定义规范（强制）**
>
> - 路径中**禁止使用中文**、大写字母、下划线（单词间用短横线 `-` 分隔）。
> - 路径层级**不超过 4 级**（不含前缀），例如 `/业务域/子模块/{id}/操作` 已为上限，禁止更深嵌套。
> - 同一功能模块内，所有接口的**业务域与子模块前缀必须一致**，不得混用不同前缀。
> - 若复用现有接口，须在备注列中标注「复用现有接口，见现有业务说明.spec.md §X.X」，不得重复定义。
> - 接口路径在 PRD 评审通过后即作为后端 Controller 的**路径基准**，技术设计阶段不得随意更改；如需变更须在 PRD 中更新并注明变更原因。

### 3.5 非功能需求（可选但建议）

- **性能/数据量**：预期并发、数据量级（若相关）。
- **安全与权限**：是否新权限标识、数据权限要求。**角色定义、数据范围、部门树层级、审批链路等一律以 `需求梳理/第0阶段-多端权限架构/全局-角色与权限体系.md` 为唯一基准**，不得在单个 PRD 中重新定义或变更角色编码、数据范围规则；如需新增角色或调整权限架构，须先修订该全局文档并经评审通过。
- **兼容性**：与现有 Web/App、浏览器或客户端的兼容要求。

### 3.6 验收标准

- **验收条件**：可检查的条目（如「用户能通过 XX 入口完成 YY 操作并看到 ZZ 结果」）。
- **原型对照**：关键界面/流程以「见可交互 HTML 原型」标注，便于评审时对照。

### 3.7 附录（可选）

- 调研笔记、现有接口列表、与竞品/历史方案对比等。

## 五、与现有规范的关系

- **先产品、后技术**：本约束负责「做什么、给谁用、长什么样」；技术实现仍遵循 `doc_spec/项目整体代码约束.spec.md`、`doc_spec/现有数据库说明.spec.md`、`doc_spec/现有业务说明.spec.md` 等。
- **角色与权限体系**：所有 PRD 中涉及角色定义、角色编码、数据范围、部门树设计、菜单权限规则、审批链路的内容，**统一以 `需求梳理/第0阶段-多端权限架构/全局-角色与权限体系.md` 为唯一权威来源**。PRD 中仅引用该文档中的角色编码与名称，不得自行定义、重命名或变更角色体系。若业务需要新增角色或调整权限架构，须先修订全局权限文档并经评审通过，再在 PRD 中引用。
- **调研依据**：调研阶段以 `doc_spec/现有业务说明.spec.md` 为现有功能基线，必要时结合代码与接口实际行为补充。
- **OpenSpec 流程**：若采用 `openspec/changes/<变更名>/` 做技术设计，则 PRD 与可交互 HTML 原型应在 `design.md` / `proposal.md` 之前完成并评审通过；PRD 可放在该变更目录下（如 `prd.md`），原型放在同目录 `prototype/`。

# 项目整体代码约束

本文档为 **蓬溪县生猪数字化管理平台** 项目整体代码生成与开发规范，适用于前后端协作、接口约定与目录结构。子规范见 `doc_spec/front/`、`doc_spec/service/`。

---

## 一、项目结构约定

### 1.1 仓库与模块

- **根目录**：多模块单体仓库，包含 `service/`（后端）、`web/`（前端）、`doc_spec/`（规范文档）。
- **后端**：`service/` 下 Maven 多模块，主入口为 `ruoyi-admin`，核心为 `ruoyi-framework`、`ruoyi-system`、`ruoyi-common`，可选 `ruoyi-quartz`、`ruoyi-generator`。根据功能领域可新建模块（如 `ruoyi-order`、`ruoyi-payment`）。
- **前端**：`web/` 下 Vue 3 + Vite + TypeScript，Element Plus UI。

### 1.2 技术栈锁定

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 后端语言 | Java 8 | 不得擅自升级 JDK |
| Web 框架 | Spring Boot 2.5.x | 与当前依赖版本一致 |
| 安全框架 | Spring Security + JWT | Token 认证机制 |
| ORM | MyBatis + MyBatis-Plus | 根据业务需求选择；需数据权限时用 XML，简单 CRUD 可选 MP 或 XML |
| 分页 | PageHelper | 保留现有 `startPage()` + `getDataTable(list)` 用法（详见分页规则） |
| 接口文档 | Swagger3 + Knife4j | 按环境开关：开发/测试开启，生产关闭 |
| 文件存储 | Minio | 统一使用 `/common/uploadMinio`，禁止使用本地存储 |
| 缓存 | Redis | 配合 `RedisCache` 工具类使用 |
| 数据源 | Druid | 支持多数据源配置 |
| 前端框架 | Vue 3 + TypeScript | Composition API + `<script setup>` |
| 构建 | Vite 6.x | 不改为 Webpack |
| UI | Element Plus | 组件与主题与现有一致 |

**系统需求**（参考 [RuoYi-Vue 官方文档](https://doc.ruoyi.vip/ruoyi-vue/)）：
- JDK >= 1.8
- MySQL >= 5.7
- Redis >= 3
- Maven >= 3.0
- Node >= 12

### 1.3 规范文档与优先级

1. **项目已有代码与本仓库规范**（最高优先级）：目录结构、命名、分层、注解用法以现有实现为准。
2. **doc_spec 下的规范文档**：本文及其余规范见下方 **五、文档索引**（含前端、后端、数据库、系统业务、Git 提交等）。
3. 框架官方最佳实践与通用编码规范（不与之冲突时遵循）。

**原则**：发现项目代码问题时，仅修复问题，不擅自做大范围重构或更换技术栈。

## 二、前后端协作约定

### 2.1 接口协议

- **Base URL**：开发环境通过 Vite 代理 `/dev-api` 转发至后端（如 `http://localhost:8080`）。
- **认证**：请求头 `Authorization: Bearer <token>`，Token 由登录接口返回并持久化（如 Cookie/LocalStorage）。
- **统一响应**：
  - 普通接口：`{ code, msg, data }`（`AjaxResult`），成功 `code = 200`。
  - 分页表格：`{ code, msg, total, rows }`（`TableDataInfo`），`rows` 为当前页列表。
- **分页参数**：`pageNum`（从 1）、`pageSize`、`orderByColumn`、`isAsc`，与后端 `TableSupport` / `PageDomain` 一致。

### 2.2 错误与状态码

- `200`：成功。
- `401`：未登录或 Token 过期，前端统一跳转登录。
- `403`：无权限访问。
- `500`：服务器错误，前端展示 `msg`。
- 其他业务码：以后端约定为准，前端按 `code` 与 `msg` 展示。

**错误提示处理**：
- 前端统一在 `@/utils/request` 响应拦截器中处理错误，根据 `code` 显示对应提示。
- 后端通过 `GlobalExceptionHandler` 全局异常处理器返回统一格式。

### 2.3 命名与风格

- **URL**：REST 风格，小写，单词用 `-` 或直接拼接（与现有一致），如 `/system/user/list`、`/system/role/{id}`。
- **字段名**：后端 Java 驼峰，JSON 序列化保持驼峰；前端 TS/JS 驼峰，与后端字段一一对应（如 `userId`、`createTime`）。

## 三、目录与文件约定（概要）

### 3.1 后端（详见 doc_spec/service/后端主要约束.spec.md）

- **Controller 按客户端类型区分**：
  - `com.ruoyi.web.controller.**`：WEB 管理后台接口（PC 端）
    - **现有功能**：保持原有 URL 不变（如 `/system/user`、`/monitor/online`）
    - **新增功能**：使用 `/web/**` 前缀（如 `/web/breeding/info`、`/web/enterprise`）
  - `com.ruoyi.app.controller.**`：APP 移动端接口（URL 前缀 `/app/**`）
  - `com.ruoyi.applet.controller.**`：小程序接口（URL 前缀 `/applet/**`）
- **Controller 职责**：只做参数校验与调用 Service，返回 `AjaxResult` 或 `TableDataInfo`；不同客户端可复用 Service 层。
- **业务模块目录结构**（必须严格遵守）：
  - `domain/`：实体类（数据库映射）
  - `domain/vo/`：视图对象（返回前端）
  - `domain/dto/`：数据传输对象（接收前端参数）
  - `mapper/`：MyBatis Mapper 接口
  - `service/`：服务接口（`IXxxService`）
  - `service/impl/`：服务实现类（`XxxServiceImpl`）
  - `resources/mapper/模块名/`：MyBatis XML 映射文件
- **Mapper**：接口在 `**/mapper/`，XML 在 `resources/mapper/**/*Mapper.xml`，可与 MyBatis-Plus 的 `BaseMapper` 共存。
- **分页**：沿用 `PageUtils.startPage()` + `getDataTable(list)`，不改变前端入参与返回结构。
- **分页规则（重要）**：
  - **前提**：`startPage()` 只能在继承了 `BaseController` 的 Controller 中使用。
  - `startPage()` 后按**代码执行顺序**，**第一个执行的查询 SQL** 会被分页（不管是方法调用中的查询还是直接查询）。
  - **确保第一个查询是要分页的**：`startPage()` 后第一个执行的 SQL 必须是需要分页的列表查询。
  - **非分页查询放在 startPage() 之前**：权限校验、获取配置等不需要分页的查询，必须放在 `startPage()` **之前**。
  - **列表查询前置条件规则（必须）**：若列表查询前需要查询其他条件，必须在 `startPage();` **之前**执行；或改为在同一条列表 SQL 中通过联表查询一次完成。
  - **使用 startPage() 时分页 SQL 不能手写 LIMIT**：PageHelper 会自动追加，手写会冲突。
  - **不使用 startPage() 时可手写分页**：如导出全量或特殊分页逻辑，可在 SQL 中写 `LIMIT`。
  - 详细用法见 `doc_spec/service/后端主要约束.spec.md` 第七节"分页"。

### 3.2 前端（详见 doc_spec/front/前端主要约束.spec.md）

- **页面**：`web/src/views/` 按业务分目录（如 `system/user`、`monitor/operlog`）。
- **API**：`web/src/api/` 与后端模块对应，按接口分文件（如 `system/user.ts`）。
- **类型**：`web/src/types/`，与后端实体和接口响应一致，`api` 中通过 `@/types` 引用。
- **请求**：统一使用 `@/utils/request` 封装的 axios 实例，自动带 Token 与错误处理。

## 四、安全与质量

- **权限**：后端接口使用 `@PreAuthorize` 与权限标识（如 `system:user:list`）；前端按钮/菜单使用 `v-hasPermi` 等指令与后端一致。
- **按需注解**：以下注解仅在需求**明确要求**或**符合条件**时添加，默认不生成：
  - `@PreAuthorize`（权限字符）：WEB 接口有菜单时添加；APP/小程序接口通常无菜单，默认不加。
  - `@Log`（操作日志）：仅当需求要求记录操作日志时添加。
  - `@DataScope`（数据权限）：仅当需求要求数据权限控制时添加（详见下方说明）。
- **数据权限使用说明（@DataScope）**：当需求要求"按部门/用户过滤数据"时使用：
  - **使用条件**：需求明确要求"只能看本部门数据"、"只能看自己的数据"等行级数据过滤。
  - **权限类型**（由角色 `sys_role.data_scope` 字段配置）：
    - `1` 全部数据权限：可查看所有数据
    - `2` 自定数据权限：可查看指定部门的数据（需配置 `sys_role_dept`）
    - `3` 本部门数据权限：只能查看本部门数据
    - `4` 本部门及以下数据权限：可查看本部门及所有子部门数据
    - `5` 仅本人数据权限：只能查看自己的数据
  - **两种使用方式**：
    - **列表查询**：Service 方法加 `@DataScope` 注解 + Mapper XML 添加 `${params.dataScope}`
    - **单条操作**：Controller 中调用 `checkXxxDataScope(id)` 校验详情/修改/删除的数据权限
  - **必须用 XML**：数据权限场景**必须**使用 MyBatis XML 写法，**不能**用 MyBatis-Plus Wrapper。
  - **特殊规则**：超级管理员（admin）不受数据权限限制；多角色取并集；自定权限需配置 `sys_role_dept`。
  - **详细用法**：见 `doc_spec/service/后端主要约束.spec.md` 的"4.2 数据权限使用说明"章节。
- **敏感信息**：密码、密钥等不入库明文、不写死在前端；生产环境关闭 Swagger/Knife4j（`swagger.enabled=false`）。
- **代码风格一致**：生成的代码**必须**与现有代码风格格式保持一致，包括但不限于：缩进、命名、注解使用、方法结构、异常处理方式等。新增代码前应先参考同模块或同类型的现有代码，确保风格统一。
- **注释要求**：
  - **生成的代码必须有注释**：公共类、接口、Controller/Service/Mapper 的公共方法均应有 JavaDoc。
  - **复杂逻辑必须写注释说明**：多分支判断、业务规则、状态流转、非显而易见的计算或查询条件等，必须在代码处用注释说明**为什么这样做**、**约束条件**或**注意点**。
  - 与前端/数据库约定处、易混淆的字段或常量，必须加注释说明。
- **Swagger 注解必须**：生成的 Controller 接口**必须**添加 Swagger 注解（`@Api`、`@ApiOperation`、`@ApiImplicitParam` 等）；实体/VO/DTO 字段**必须**添加 `@ApiModelProperty` 注解，确保接口文档完整。
- **接口文档生成优先级**：生成的接口**必须**严格遵循以下优先级：
  1. **接口文档优先**：若已提供接口文档，严格按照文档中的 URL、参数、返回值等定义生成。
  2. **需求/PRD 次之**：若无接口文档，按照需求文档或 PRD 中的描述生成。
  3. **现有接口兜底**：若以上都无，参照现有同类型接口的风格和规范生成。
- **必填字段校验**：新增、修改等接口的必填字段**必须**进行校验：
  - **后端**：专用 DTO/VO 使用 `@NotNull`、`@NotBlank` 等注解校验；复用类/公共类在 Service 层用代码校验。
  - **前端**：表单必填项使用 Element Plus 的 `rules` 进行校验，提交前验证通过。
  - **必填项来源**：根据需求文档确定，不得遗漏。
- **值范围校验**：枚举值、状态、类型等有限值字段**必须**校验传入值是否合法：
  - **后端**：使用 `@Pattern` 注解或在 Service 层判断值是否在允许范围内，非法值抛出异常。
  - **前端**：使用 `validator` 自定义校验或 `el-select` 下拉选择限制可选值。
  - **错误提示**：校验失败时返回清晰信息，说明允许的值范围。
- **安全性、性能与并发**：生成的代码**必须**考虑：
  - **安全性**：SQL 注入防护（参数化查询）、越权访问校验、敏感数据保护、接口幂等性。
  - **性能**：避免 N+1 查询、大数据量分页、合理使用缓存、避免大事务。
  - **并发**：乐观锁/悲观锁、数据库唯一约束、分布式锁、原子操作。
- **数据库表同步**：每次有**新表设计**或**表结构增加/变更**，须同步在 `doc_spec/现有数据库说明.spec.md` 中记录（表名、说明、主键、字段说明），并在 `service/sql` 下维护或补充建表脚本，保证文档与库表一致。
- **业务说明同步**：每次有**新业务功能**或**现有业务变更（新增、修改、删除接口/功能）**，须同步在 `doc_spec/现有业务说明.spec.md` 中更新（功能说明、接口路径、前后端对应关系），保证文档与实际业务一致。
- **数据库字段注释必须**：所有数据库表的每个字段**必须**添加 `COMMENT` 注释，说明字段含义、取值范围或业务用途；每张表**必须**有表级 `COMMENT` 说明表的业务用途。无注释的表结构设计不予接受。
- **数据字典与菜单 SQL**：涉及数据字典（状态、类型等枚举值）或菜单权限的功能，**必须**生成对应初始化 SQL 脚本（放入 `service/sql/`），包括字典类型、字典数据、菜单及按钮权限。
- **前后端启动与部署**：前后端为完全分离架构，开发与部署都必须保证前后端分别可用后再联调或验收。
- **NPM 源注意**：建议使用 npm 官方或 `npmmirror` 源；禁止使用 `cnpm`（可能出现依赖解析与构建异常）。
- **环境变量生效规则**：前端 `.env.*` 或后端配置项修改后，必须重启对应服务，禁止以“热更新已生效”作为验收依据。
- **反向代理注意**：Nginx 代理除业务前缀（如 `/prod-api`）外，需同步代理 `/v3/api-docs/*`，避免 Knife4j/Swagger3 在代理环境下不可用。
- **子路径部署**：存在应用子路径时，后端 `context-path` 与前端路由/资源基础路径必须一致配置，禁止前后端路径前缀不一致上线。
- **前端鉴权边界**：前端权限控制仅作展示与交互限制，不能替代后端鉴权；后端必须独立进行权限校验。

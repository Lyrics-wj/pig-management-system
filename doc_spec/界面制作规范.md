# 界面制作规范

本文档规定 **2024年蓬溪县生猪数字化管理平台** 项目通过 PRD 文档创建纯前端 HTML 原型界面的全套规范，适用于所有原型制作场景。

---

## 一、适用范围

- 所有基于 PRD 文档制作的可交互 HTML 原型界面。
- 与 `doc_spec/PRD设计规范.spec.md` 第四章「可交互 HTML 原型要求」配套使用，本规范在其基础上进一步细化。

---

## 二、制作前置流程

### 2.1 PRD 理解确认

在开始制作 HTML 原型前，必须完整阅读所有相关 PRD 文档，并按以下规则处理问题：

1. **单个 PRD 文件**：直接阅读并按规范制作，无需提前确认。
2. **多个 PRD 文件**：
   - 充分理解各 PRD 的功能边界与交互逻辑。
   - 发现以下情形时，**必须通过提问方式与用户确认，每次最多提出 5 个问题**，确认后再制作：
     - PRD 描述存在矛盾或歧义。
     - 不同 PRD 之间存在数据或流程依赖但未说明关联规则。
     - 关键业务规则不明确，导致无法完善模拟数据或交互逻辑。
     - 涉及角色权限但 PRD 中未明确各角色的功能边界。
3. **禁止**：在未理解 PRD 的情况下直接生成界面，或对 PRD 中有歧义的内容做主观假设后直接制作。

### 2.2 制作范围确认

**每次制作 HTML 原型前，必须由用户明确指定 PRD 来源**，规则如下：

1. **指定文件夹**：用户给出一个存放 PRD 的文件夹路径，则需读取该文件夹下的**所有 `.prd.md` 文件**，逐一生成对应的 HTML 文件。
2. **指定文件**：用户给出一个或多个具体的 PRD 文件路径，则仅生成对应文件的 HTML，不处理同目录下的其他 PRD 文件。
3. **未指定来源**：若用户未提供任何文件夹或文件路径，**必须停止并提示用户指定后再继续**，提示语参考：

   > 请告诉我需要制作哪些 PRD 文件的原型界面，可以指定：
   > - 一个文件夹路径（将生成该文件夹下所有 PRD 的 HTML）
   > - 一个或多个具体的 PRD 文件路径
   
   **禁止**在未收到明确来源指定的情况下自行假设范围或开始生成。

开始制作前还需明确：
- 是否涉及多角色（需确认各角色的功能权限差异）。
- 是否涉及多端口/多系统入口（需确认各端口的功能差异）。
- 制作完成后是否需要更新入口 `index-XXX.html` 文件。

## 三、技术栈规范

### 3.1 允许使用的技术

| 技术 | 用途 | 引入方式 |
|------|------|---------|
| 原生 HTML5 + CSS3 | 结构与样式基础 | 直接编写 |
| Tailwind CSS | 快速样式布局 | CDN |
| Font Awesome | 图标 | CDN |
| Alpine.js | 轻量级交互逻辑 | CDN |
| Chart.js | 图表展示（如有统计功能） | CDN |
| 原生 JavaScript (ES6+) | 复杂交互逻辑 | `<script>` 内联或同目录文件 |

### 3.2 禁止使用的技术

- 重型框架（Vue、React、Angular 等）。
- 需要构建工具的任何技术。
- 依赖本地服务器才能运行的方案（必须支持直接用浏览器打开 `.html` 文件）。
- 本地文件 import/require（所有脚本必须内联或通过 CDN 引入）。

### 3.3 推荐 CDN 地址

```html
<!-- Tailwind CSS -->
<script src="https://cdn.tailwindcss.com"></script>

<!-- Font Awesome -->
<link rel="stylesheet" href="https://cdnjs.cloudflare.com/ajax/libs/font-awesome/6.5.0/css/all.min.css">

<!-- Alpine.js -->
<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3.x.x/dist/cdn.min.js"></script>

<!-- Chart.js（按需引入） -->
<script src="https://cdn.jsdelivr.net/npm/chart.js"></script>
```

## 四、文件组织规范

### 4.1 目录结构

PRD 文件与原型 HTML 文件采用**镜像目录结构**，`原型图/` 文件夹与 PRD 所在文件夹**同级或位于其上级**，内部按 PRD 所在子文件夹路径创建同名文件夹后存放 HTML 文件。

**`原型图/` 文件夹的定位规则：**

从 PRD 文件所在目录开始，**向上逐级查找**，以第一个找到 `原型图/` 文件夹的位置为准；若整个向上路径中均不存在 `原型图/`，则在 PRD 文件所在目录的**同级**新建 `原型图/` 文件夹。

**示例一：`原型图/` 与 PRD 文件夹同级**

```
doc_prd/
└── WEB/
    └── 企业端/
        ├── WEB企业端-信息填报-养殖信息.prd.md
        └── WEB企业端-信息填报-繁育信息.prd.md

原型图/                              ← 与 doc_prd/ 同级
├── index-信息填报.html               ← 入口文件，按功能命名
└── WEB/
    └── 企业端/                      ← 镜像 PRD 子文件夹路径
        ├── WEB企业端-信息填报-养殖信息.html
        └── WEB企业端-信息填报-繁育信息.html
```

**示例二：`原型图/` 位于 PRD 文件夹的上级**

```
项目根目录/
├── 原型图/                          ← 位于更上级，优先使用此处
│   ├── index-信息填报.html           ← 入口文件，按功能命名
│   └── WEB/
│       └── 企业端/
│           ├── WEB企业端-信息填报-养殖信息.html
│           └── WEB企业端-信息填报-繁育信息.html
└── doc_prd/
    └── WEB/
        └── 企业端/
            ├── WEB企业端-信息填报-养殖信息.prd.md
            └── WEB企业端-信息填报-繁育信息.prd.md
```

**目录创建规则：**
- 存放 HTML 文件前，先按上述规则定位 `原型图/` 文件夹；若不存在，在 PRD 所在目录**同级**新建 `原型图/` 文件夹。
- `原型图/` 内部的子目录路径与 PRD 文件相对于 `doc_prd/`（或对应 PRD 根目录）的路径保持一致；子目录不存在时**必须先创建再存放文件**。
- `原型图/` 根目录下必须存在对应功能的入口文件（命名规则见 4.2）。

### 4.2 文件命名规范

- **功能 HTML 文件**：文件名与对应 PRD 文件名相同，仅将扩展名 `.prd.md` 替换为 `.html`，禁止自行缩短或重命名。
  - 示例：`WEB企业端-信息填报-养殖信息.prd.md` → `WEB企业端-信息填报-养殖信息.html`
- **入口导航文件**：命名格式为 `index-{功能名称}.html`，功能名称取本次制作所涵盖功能模块的简短中文名称。
  - 示例：制作信息填报模块 → `index-信息填报.html`；制作项目管理模块 → `index-项目管理.html`
  - 若用户有特殊命名要求，以用户指定的名称为准，不受上述格式约束。
  - 每次制作一批功能时生成一个对应的入口文件；若本次制作涉及多个不同模块，可分别生成各模块的入口文件。
- 禁止使用裸名 `index.html`（无功能名称后缀），除非用户明确要求。

### 4.3 入口文件规范

每次新增或修改 HTML 原型文件后，**必须同步更新对应的 `index-{功能名称}.html`**，要求：

1. **内容结构**：
   - 项目名称与版本信息。
   - 按系统端口分组，每个端口下按功能模块列出所有原型页面。
   - 每个页面条目包含：页面名称、对应 PRD 文件名、功能描述摘要、最后更新时间。
2. **跳转方式**：所有页面链接使用相对路径，支持直接点击跳转。
3. **状态标注**：每个页面标注制作状态（✅ 已完成 / 🚧 制作中 / 📋 待制作）。
4. **角色入口**：若涉及多角色，在入口页面提供角色切换选择，选择后进入对应角色的系统首页。
5. **存放位置**：入口文件必须位于 `原型图/` 根目录下，路径为 `原型图/index-{功能名称}.html`。

## 五、HTML 文件内部结构规范

### 5.1 文件头部必备信息

每个 HTML 文件顶部必须包含注释说明：

```html
<!--
  功能名称：XXX
  对应PRD：doc_prd/XXX/XXX.prd.md
  所属端口：WEB企业端 / WEB政府端 / APP端
  所属模块：信息填报 / 统计分析 / 系统管理 / ...
  制作日期：YYYY-MM-DD
  最后更新：YYYY-MM-DD
  角色说明：养殖场管理员、政府监管员（如涉及多角色）
-->
```

### 5.2 Mock 数据规范

**所有模拟数据必须集中定义在 `<script>` 顶部的 `const MOCK_DATA = {}` 中**，严格禁止将数据散落在 DOM 或函数内部。

```javascript
const MOCK_DATA = {
  // 当前登录用户信息
  currentUser: {
    id: 1,
    name: '张三',
    role: 'farm_admin',      // 角色标识
    roleName: '养殖场管理员',
    farmId: 101,
    farmName: '蓬溪县鑫源养殖场',
    permissions: ['read', 'write', 'export']
  },

  // 按功能模块分组的业务数据
  pigRecords: [...],         // 生猪记录
  farmList: [...],           // 养殖场列表
  vaccineRecords: [...],     // 防疫记录

  // 枚举字典数据（与 PRD 3.4.2 字段定义的枚举值严格一致）
  dict: {
    pigBreed: [              // 猪品种
      { value: '01', label: '长白猪' },
      { value: '02', label: '大白猪' },
      ...
    ],
    pigStatus: [             // 状态
      { value: '0', label: '正常' },
      { value: '1', label: '异常' }
    ]
  }
};
```

**Mock 数据生成要求：**
- 数量：列表类数据至少 8 条，覆盖不同状态/类型的枚举值。
- 字段完整性：每条数据必须包含 PRD 3.4.2 中定义的全部字段，不得省略。
- 逻辑严密性：数据间的关联关系必须合理（如关联 ID 可以对应找到记录，日期范围合法，数值在有效范围内）。
- 状态覆盖：至少覆盖 PRD 中定义的全部业务状态枚举值。
- 禁止：使用无意义的随机数据（如"xxx"、"测试数据1"、"aaa"等）。

### 5.3 区块结构规范

页面中每个主要功能区块必须按以下规范组织：

```html
<!-- SECTION START: 功能区块名称 -->
<section id="feature-xxx" ...>
  <!-- 区块内容 -->
</section>
<!-- SECTION END: 功能区块名称 -->
```

所有功能区块的 `id` 命名格式：`feature-{功能英文名}`，例如：
- `#feature-login`：登录功能
- `#feature-list`：列表查询
- `#feature-add-modal`：新增弹窗
- `#feature-edit-modal`：编辑弹窗
- `#feature-detail`：详情页
- `#feature-filter`：筛选条件区
- `#feature-stats`：统计图表区

## 六、交互功能规范

### 6.1 可交互性要求（强制）

所有生成的 HTML 界面必须满足以下可交互性要求：

| 功能类型 | 必须实现的交互 |
|---------|--------------|
| 列表页 | 分页切换、排序点击、筛选条件联动、行操作按钮响应 |
| 新增/编辑 | 表单输入、必填校验、格式校验、提交模拟（alert/console） |
| 详情查看 | 弹窗或抽屉展开、数据完整展示 |
| 删除操作 | 二次确认弹窗、确认后从列表移除（前端模拟） |
| 状态切换 | 点击后状态即时更新、按钮文案/样式同步变化 |
| 搜索/筛选 | 关键词过滤列表数据、条件组合查询 |
| 导出按钮 | 点击后弹窗提示"导出成功"或模拟下载行为 |
| 导入按钮 | 文件选择框，点击后模拟导入成功提示 |

### 6.2 Tab 页签规范（强制）

凡页面存在 Tab 页签的，必须满足：

1. **全量实现**：所有 Tab 页签对应的功能界面必须按 PRD 逐一完善，不得有任何 Tab 仅作占位展示（"内容待完善"、"暂无数据"视为未实现）。
2. **即时切换**：点击 Tab 立即切换显示内容，无需点击额外按钮。
3. **独立数据**：每个 Tab 使用各自的 `MOCK_DATA` 分区数据，数据互不干扰。
4. **状态保持**：同一页面中切换 Tab 不重置其他 Tab 的筛选条件或分页状态。
5. **选中样式**：当前激活 Tab 有明显视觉区分（不同背景色、下划线等）。

### 6.3 表格操作列规范（强制）

凡页面存在数据表格的，操作列必须满足：

1. **按钮完整**：PRD 中定义的所有操作按钮（查看、编辑、删除、审核、导出等）必须全部实现，不得遗漏任何一个。
2. **固定不滚动**：操作列必须固定在表格最右侧，当表格列数较多需要横向滚动时，操作列保持不动，其余数据列可横向滚动。实现方式：表格容器设置 `overflow-x: auto`，操作列使用 `position: sticky; right: 0` 固定，并设置与表格背景一致的背景色防止透视。
3. **权限控制**：不同角色对同一行数据的可操作按钮不同时，必须按角色进行显示/隐藏控制。
4. **状态联动**：操作按钮的可用性应与数据当前状态联动（如"已审核"状态下不显示"编辑"按钮）。
5. **确认提示**：破坏性操作（删除、撤销等）必须有二次确认弹窗，提示信息具体（包含记录标识，如"确认删除编号为 PIG-2024-001 的记录吗？"）。
6. **操作反馈**：每个操作执行后必须有明确的结果反馈（成功提示、列表刷新等）。

### 6.4 表单规范（强制）

1. **字段完整**：表单字段必须与 PRD 3.4.2 数据模型字段完全对应，逐一实现，不得遗漏。
2. **只读字段**：系统自动生成或关联回显的字段（编号、创建时间、创建人等）必须渲染为禁用态，视觉上与可编辑字段明显区分。
3. **前端校验**：
   - 必填字段：提交前检查，未填写时在字段下方显示"XXX 不能为空"提示。
   - 格式校验：手机号、身份证号、日期等有格式要求的字段，失焦（blur）时即时校验并给出具体提示。
   - 业务逻辑校验：结束时间≥开始时间、数值在有效范围内等，提交前进行联动校验。
4. **枚举字段**：所有枚举类型字段使用下拉框（`<select>`），下拉选项与 PRD 3.4.2 字段枚举值完全一致。
5. **日期字段**：使用原生 `<input type="date">` 或带日历选择的控件，不得使用文本框代替。

### 6.5 登录功能规范（强制）

凡涉及登录界面的系统，必须满足：

1. **多端口区分**：若系统存在多个端口（WEB企业端、WEB政府端、APP等），不同端口必须有独立的登录入口，登录后进入对应端口的功能界面。
2. **功能差异验证**：不同端口登录进入系统后，菜单导航和功能权限必须严格按照 PRD 定义进行区分展示。
3. **登录校验**：
   - 必填校验：用户名和密码为必填项，空提交时给出提示。
   - 账号验证：在 `MOCK_DATA` 中预设多个账号，输入正确账号密码才能登录成功，错误时给出"用户名或密码错误"提示。
4. **登录成功**：登录成功后跳转到对应角色/端口的系统首页，顶部/侧边显示当前登录用户信息。
5. **退出登录**：系统内提供退出登录按钮，点击后返回登录页。

### 6.6 多角色切换规范（强制）

凡 PRD 中涉及多个角色操作同一系统的，必须满足：

1. **角色切换入口**：在系统右上角（或 `index-{功能名称}.html` 入口处）提供"切换角色"功能，支持在多个预设角色间切换。
2. **功能差异体现**：切换角色后，以下内容必须随之变化：
   - 导航菜单（显示/隐藏对应角色可见的菜单项）。
   - 操作按钮（显示/隐藏对应角色可操作的按钮）。
   - 数据范围（如养殖场管理员只能看到本场数据，政府监管员可看到全部数据）。
3. **预设角色账号**：在 `MOCK_DATA` 中预设每个角色对应的账号，格式如下：

```javascript
const MOCK_DATA = {
  users: [
    { id: 1, username: 'admin001', password: '123456', role: 'farm_admin', roleName: '养殖场管理员', farmId: 101 },
    { id: 2, username: 'gov001',   password: '123456', role: 'gov_officer', roleName: '政府监管员', deptId: 201 },
    { id: 3, username: 'super',    password: '123456', role: 'super_admin', roleName: '超级管理员', deptId: 0 }
  ]
};
```

4. **当前角色标识**：界面始终显示当前操作角色的名称，不得隐藏。

## 七、界面风格规范

### 7.1 整体风格

全部原型界面采用统一的视觉风格，确保各功能页面保持一致的外观和交互感受。

**基础色调：**
- 主色：`#1677ff`（蓝色，政务系统风格）
- 背景色：`#f0f2f5`（浅灰背景）
- 卡片背景：`#ffffff`（白色）
- 边框色：`#e8e8e8`
- 文字主色：`#262626`
- 文字次色：`#595959`
- 文字辅色：`#8c8c8c`

**状态色：**
- 成功/正常：`#52c41a`（绿色）
- 警告/待处理：`#faad14`（橙色）
- 错误/异常：`#ff4d4f`（红色）
- 禁用：`#bfbfbf`（灰色）

### 7.2 组件风格统一要求

| 组件 | 规范要求 |
|------|---------|
| 按钮 | 主操作用蓝色实心按钮，次操作用白色描边按钮，危险操作用红色按钮 |
| 表格 | 带斑马纹（奇偶行颜色区分），表头灰色背景，hover 行有高亮；**操作列固定在最右侧不随横向滚动移动，其余列超出宽度时横向滚动** |
| 弹窗 | 统一使用居中模态弹窗，有半透明遮罩，顶部标题+右上角关闭按钮 |
| 表单 | 标签右对齐，输入框统一宽度，必填项标签前有红色星号 `*` |
| 分页 | **固定在内容区域底部，不随数据区域滚动；数据列表在上方独立滚动，分页器始终可见** |
| 状态标签 | 使用带颜色的小圆角标签（badge/tag），颜色与状态色对应 |
| 面包屑 | 多级页面顶部显示面包屑导航 |
| 顶部导航栏 | 固定顶部，左侧系统名称/Logo，右侧用户信息+退出按钮 |
| 侧边菜单 | 固定左侧，支持折叠，当前激活菜单高亮 |

### 7.3 布局结构

**PC 端管理系统标准布局：**
```
┌─────────────────────────────────────────────┐
│  顶部导航栏（固定，高度 60px）                 │
├──────────┬──────────────────────────────────┤
│          │  面包屑导航                        │
│  侧边     ├──────────────────────────────────┤
│  菜单     │  页面标题 + 操作按钮区             │
│  (240px) ├──────────────────────────────────┤
│          │  筛选条件区                        │
│          ├──────────────────────────────────┤
│          │  数据列表/内容区（可独立纵向滚动）   │
│          ├──────────────────────────────────┤
│          │  分页器（固定底部，始终可见）        │
└──────────┴──────────────────────────────────┘
```

**自适应要求（强制）：**

所有页面必须满足基本的自适应需求，确保在主流屏幕宽度下均可正常使用：

- **最小支持宽度**：1280px，低于此宽度时页面允许横向滚动，不得出现内容被遮挡或错乱。
- **内容区弹性**：侧边菜单宽度固定（240px / 折叠态 60px），内容区宽度随窗口剩余空间自动伸缩，不得固定内容区像素宽度。
- **表格自适应**：表格容器宽度跟随内容区自动伸缩；当列数较多导致内容超出容器宽度时，启用横向滚动（见 7.2 表格规范），不得让表格溢出撑破布局。
- **弹窗自适应**：弹窗宽度建议使用百分比或 `max-width` 限制，在窄屏下不超出视口宽度，保留左右边距不小于 16px。
- **字号与间距**：不得使用绝对像素定义字号和间距（`px` 仅用于边框、图标等固定元素），正文字号不低于 13px。

## 八、各类功能页面制作要点

### 8.1 列表查询页

必须包含以下区域：
1. **筛选区**：根据 PRD 3.4.3 定义的筛选条件，逐一实现筛选控件（日期范围、下拉筛选、关键词搜索等），筛选条件变化后自动或点击"查询"按钮刷新列表。
2. **工具栏**：新增按钮（若有）、批量操作按钮（若有）、导出按钮（若有）、导入按钮（若有）。
3. **数据表格**：
   - 列定义与 PRD 字段一一对应，不得遗漏重要展示列。
   - 操作列固定在最右侧，不随横向滚动移动（见第六章 6.3）。
   - 表格区域独立纵向滚动，不影响分页器位置。
   - 表格支持分页，默认每页 10 条。
4. **分页器**：固定在列表区域底部，始终可见，不随表格数据区域滚动；显示总条数、当前页码、每页条数，支持翻页操作（前端模拟分页切换）。

### 8.2 新增/编辑弹窗或页面

1. 弹窗标题：新增场景为"新增 XXX"，编辑场景为"编辑 XXX"。
2. 表单字段：严格按照 PRD 3.4.2 数据模型全量实现（见第六章 6.4）。
3. 底部按钮：取消（关闭弹窗）+ 确定/保存（触发校验并模拟提交）。
4. 提交成功后：关闭弹窗并刷新列表（前端模拟，将新数据追加或更新到 `MOCK_DATA` 中）。

### 8.3 详情页/查看弹窗

1. 所有字段以"标签: 值"格式展示，不允许空值不展示（空值显示"——"）。
2. 多级关联数据完整展示（不仅显示 ID，还需显示关联名称）。
3. 若详情页有操作按钮（编辑、审核、驳回等），需按权限控制可见性。

### 8.4 统计图表页

1. 使用 Chart.js 渲染图表，图表类型与 PRD 中定义的保持一致（折线图/柱状图/饼图/雷达图）。
2. 图表数据来自 `MOCK_DATA`，数据结构合理，时间序列连续，数值有业务意义。
3. 图表标题、坐标轴标注、图例与 PRD 定义一致。
4. 若有时间范围筛选，切换时间范围后图表数据随之变化（前端模拟）。

### 8.5 审批流/状态流转页

1. 展示当前记录的审批状态和流转历史。
2. 操作按钮（通过、驳回、撤回等）按当前状态和角色权限决定是否显示。
3. 操作后状态标签即时更新。
4. 驳回操作需弹出输入驳回原因的文本框。

## 十一、PRD 问题提问规范

在阅读 PRD 发现问题时，按以下规范进行提问：

1. **提问时机**：在开始制作前提问，不得制作到一半才提问。
2. **提问数量**：单次提问不超过 5 个问题，每个问题聚焦一个具体的不明确点。
3. **提问格式**：

```
在制作 [功能名称] 的原型界面前，有以下问题需要确认：

1. [具体问题描述，注明是哪个 PRD、哪个章节、哪个字段的不明确之处]
2. [...]
...

以上问题确认后即可开始制作。
```

4. **禁止**：对有明确描述的内容进行"确认性提问"（如 PRD 中已明确说明的字段必填性、枚举值等不得重复提问）。
